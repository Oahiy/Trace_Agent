## 3. 根因如何定位

先检查需求，再沿调用链定位：问题与条件 → owner/READY 过滤 → 检索 → 上下文装载 → 模型选句 → 原文绑定 → 事务保存 → 评测。

Day 12 dev-01 的 Top-5 第一片段来自正确来源第 2 页，且确实装入上下文；E1 有七个编号句子，第 3 句同时含两个目标组成部分。旧模型返回第 1 句，内容是跨块留下的词尾和透明度/问责残片。原绑定允许长度和句尾符合约束的真实片段，因此结构检查通过，语义检查失败。

这些事实排除了“正确证据根本没找到”和“正确证据没装进去”这两个解释。它们支持先改选句指令，但不能证明所有质量问题都来自提示词。dev-03 目标表格未进入 Top-5，dev-05 受上下文和单摘录能力限制，需要分别处理。

没有加入题号判断、答案关键词、正确页码或强制返回第 3 句。新指令要求遍历候选、直接完整回答、保留否定和条件、识别残片、避免默认首句，并继续只返回编号。它改善了本次观察，不能替代通用语义验证。

## 11. 如果由你独立开发，应该注意什么

1. **先把问题写成可证伪的预期。** 明确需要两个组成部分；不能把“有引用”替代“回答完整”。AI 可帮起草，你必须核对原页和题意。
2. **逐层查证据。** 检查 Top-5、实际装入的片段、编号与返回句子。每一层分别可能失败，不凭症状更换模型或检索器。
3. **一次改变一个变量。** 先固定上下文验证指令，再验证真实链路。若同时换模型、分块和 Top-K，就很难解释收益来源。
4. **指令和程序保证分开。** JSON Schema 限制形状，绑定限制来源，模型指令影响选择；当前没有通用语义保证。不能把提示词写了什么当成系统一定做了什么。
5. **预算应属于执行过程。** 预留先于请求，失败/重试也收费；新对象不能刷新共享上限。持久失败时先阻止请求，不能先花费再补记录。
6. **外部边界要验证真实依赖。** PostgreSQL 的约束/事务、Redis、独立 worker、HTTP 故障需要相应层次测试。模型等待期间不持有业务数据库事务，保留截止和幂等语义。
7. **选择测试证据。** mock 适合固定超时、非法输出等失败路径；真实模型适合观察选择质量；本人原页核对适合确定答案含义。这三者不能互相代替。
