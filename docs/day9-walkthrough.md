## 2. 为什么没有直接把 Day 1 客户端接进业务

Day 1 的目标是确认依赖可用：模型名、256 输出上限、六次生成预算和不重试都是当日实验设定，不应被静默改造成后续业务契约。它每次请求创建客户端，并在同步入口使用 asyncio.run。

新适配器采用异步接口和可关闭的共享 AsyncClient。命令行只在最外层调用一次 asyncio.run；未来异步 API/工作流应 await 适配器，不能在已经运行的事件循环内再嵌套 asyncio.run。网络等待期间不应持有数据库事务；本日适配器完全不访问数据库。

新实现还补齐固定 768 维、输出 Schema、完成状态、失败记录、最多一次自动重试，以及可跨两个本地任务尝试保留的预算。旧实验和旧测试继续保留，不通过删除历史断言让新实现变绿。

## 3. 一次生成请求完整经过什么

1. 检查消息列表：1–16 条，全部为 Message，最后一条必须是 user。角色限定为 system/user/assistant；内容非空、不含孤立代理字符，单条最多 8000 字符。Pydantic 拒绝额外字段并冻结消息。
2. 检查输出类型必须是 BaseModel 子类，且根模型配置 extra=forbid。调用方负责定义业务字段与嵌套类型；适配器以 strict=True 验证输出，不把字符串数字强转成数字。
3. 从类型生成 JSON Schema，限制 Schema 序列化大小为 8192 字节。将 Schema 同时放入 format 和一条系统提示，生成请求明确关闭流式输出和 thinking，温度为 0，上下文配置为 4096，输出最多 1024 Token，可由调用者收紧。
4. 计算完整 wire messages 的 UTF-8 JSON 字节长度并加 256 的模板预留。超过 2800 预估单位就在网络调用前失败。系统指令和 Schema 已包含在 wire messages 内，不能只数资料正文。
5. 检查预算，访问 /api/tags 核对固定模型名和 digest。缺失、漂移或重复同名记录都拒绝；身份检查失败不算一次已发出的推理请求。
6. 发出推理前增加调用次数，预留最大允许的输入和输出用量。用同一个总截止覆盖身份读取、推理、响应读取、重试等待和下一次请求。
7. HTTP 非 200 映射安全错误，不读取或回传其原始错误正文。200 响应按流读取，累计解码字节最多 1 MiB，再严格解析 JSON，拒绝重复键和 NaN/Infinity。
8. 核验模型名、统计字段、done=true、done_reason=stop、assistant 角色和非空内容。不允许意外工具调用；length 结束原因明确报截断，不接受“前半段恰好能解析”为成功。
9. 严格解析 message.content 的 JSON，再执行调用方 Schema 校验。缺字段、额外字段、错误类型、代码围栏和重复键都失败，不自动清洗成成功。
10. 成功返回前再次核对模型库存 digest。无论成功、校验失败、超时还是取消，都在 finally 结算已知/未知用量并保留安全记录。

HTTP 200、合法 JSON、符合 Schema、来源 ID 合法、结论得到原文支持，是不同保证。本日主要交付前三层及明确的来源演示；没有把结构校验当成事实判断或医学安全验收。

## 4. Embedding 的契约

固定使用 Day 1 已验证的 nomic-embed-text:v1.5、137M/F16、768 维及完整 digest。当前本机库存报告其上下文为 2048，不能直接拿模型作者其他部署方式的长上下文参数当作本机实际能力。

| 入口 | 处理 | 返回 |
|---|---|---|
| embed_documents | 每段前加 `search_document: ` | 与输入顺序对应的多个向量 |
| embed_query | 查询前加 `search_query: ` | 一个查询向量 |

文档批次 1–8 条，单条 1–2000 字符且非空，拒绝孤立代理字符；查询遵循相同单条限制。请求显式设置 truncate=false，供应商因实际 Token 超限返回错误时不静默截断，不自动放松限制。字符限制和模型 Token 上限不是同一个概念。

返回必须数量一致、每条恰好 768 维、元素为有限 int/float，并排除 bool、NaN、Infinity、超出浮点范围的整数与全零向量。向量转为 tuple，避免调用方经别名修改结果。实现保持供应商的返回顺序；没有文档 ID 的供应商向量响应本身不能证明服务端没有交换文本，排序正确还依赖可信本机供应商契约。

返回规格包含模型名、digest、维度和 `nomic-task-prefix-v1` 处理版本。Day 10 需要把这些与索引版本对应保存；更换模型、维度、前缀或归一化方式后必须重新评估并重建相关向量，不能直接混用。同一批都是错误的 769 维也会被拒绝，不能只做“批内相等”。

余弦相似度用于比较向量方向，不是结论正确率或医学可信度。本日两个真实摘录与一个查询的相似度只作可运行性观察，没有当成 Recall/MRR 成绩。

## 5. 截止、重试和取消

适配器总截止默认 30 秒；沿用 Settings 的更短值，历史配置即使允许 120 秒，适配器也将其上限收紧到 30 秒。没有静默改掉原 Settings 的配置接受范围，实际生效规则在这里明确记录。

HTTPX 的连接上限为 min(3 秒, 总截止)，其他阶段使用已配置超时；外层 asyncio.timeout_at 限制整个操作。单次操作最多两个推理请求，底层 HTTP transport 的自动重试显式为 0。

| 情况 | 行为 |
|---|---|
| 429/502/503/504 | 最多追加一次重试，仍须有时间、请求和 Token 预算 |
| 连接、读取、写入中断、远端协议中断和 HTTPX 超时 | 同样最多一次；总截止已耗尽则不会再发请求 |
| 400/401/403/404/500、重定向 | 不重试，不跟随 Location |
| 非法 JSON、Schema 错误、截断、身份漂移 | 不重试，不修复输出 |
| 外部取消 | 传播 CancelledError，记录 model_cancelled，释放重入保护 |
| 总截止取消 | 返回 model_timeout，保留已发请求记录及预算 |

默认重试等待 0.05 秒；Retry-After 支持整数秒与有时区的 HTTP 日期。若等待时间超过剩余截止、不合法或超长，则安全停止，不忽略供应商要求立即重试。此等待只适用于受控本机开发，不是多租户高并发退避方案。

客户端取消等待不能证明 Ollama 已停止推理。读超时后再次请求也可能使服务端暂时存在重复工作；本日通过次数与截止限制风险，未声称有服务端幂等或强制取消能力。后续任务/部署层需要单独验证资源回收。

## 6. 预算为什么先预留、再结算

每个调用者持有自己的 CallBudget，不能把它做成所有用户共用的全局计数器。一次任务尝试最多四次生成请求；最多两个任务尝试，手动进入第二次时保留累计 Token、总请求数和历史记录，只重置本次尝试的生成次数。Embedding 单独计数，内部默认最多 32 次/预算对象，可以收紧。这个内部防护不是新公开 API 字段。

生成累计计费用量上限为 24000。请求发出前，预留 2800+本次输出上限；响应给出可信的非负整数用量后，分别替换输入/输出预留。未知分量保留预留值，实际用量字段保持 null，不伪造为 0。即使输出 Schema 失败，已经拿到的统计仍会结算；若供应商报告超过单次约定上限，记录真实量并拒绝结果。

例如最大输出为 1024，完全未知的失败请求保留 3824。连续六次此类请求累计 22944；即使进入第二次任务尝试，第七次也会因下一次最坏预留放不下而在发出前拒绝。测试覆盖了这一过程。

Embedding 没有输出 Token 字段，保持 null；输入未知时使用包含任务前缀的 UTF-8 字节估算与每段 32 的预留，单独保存。它也不是精确 tokenizer 统计。云 API 支出为 0，仅指本机方案没有云调用费用，不表示电力、硬件或运行时间没有成本。

CallBudget 的重入保护拒绝同一对象上的并发操作及执行期间重置尝试。它是当前进程内的可信调用方对象，不是数据库事务、线程安全配额服务、鉴权机制或持久化计费账本。next_task_attempt 不检查任务归属或 FAILED 状态；后续任务服务必须先授权、检查状态并持久恢复同一累计预算，才能调用它。进程重启后新建对象不具有恢复旧任务预算的保证。

字节估算是保守工程启发式，模板、消息和模型 tokenizer 的对应关系没有形式证明。真实长输入为 2704 预估单位、506 实际输入 Token；证明了当前样例与统计路径，不证明已经测试实际 2800 Token 的极限。过于保守的输入拒绝是当前可用性限制；后续若引入精确 tokenizer，需解释依赖、绑定模型版本、做边界实验并更新估算版本。

| 可维护性 | 通用接口、供应商实现、预算和场景演示分开；无新依赖；保留旧实验与 API 契约 |

库存检查在请求前后观测 digest，不能原子证明两次观测之间权重未被替换；仍依赖受信任的本机服务。响应字节上限和协作式 asyncio 截止也不是恶意服务的硬内存/CPU 沙箱。没有将这些开发防护写成生产级隔离承诺。

## 11. 如果由你独立开发

先只做一个输入、一个小 Schema、一个成功响应。亲手写预期，再让 AI 实现；接着主动破坏 done、字段类型、向量维度、统计和状态码，确认失败行为。随后才加入共享截止、一次重试和预算。不要一次让 AI 生成完整工作流再试图理解所有分支。

必须亲自掌握这些判断：

1. **边界职责**：API 验证身份与请求，业务层决定研究含义，适配器处理模型契约，持久层处理事务；模型等待不占 SQL 事务。来源合法与结论正确分别验收。
2. **异步资源**：理解 await、上下文管理器、客户端关闭与 CancelledError；不要吞取消或在事件循环里嵌套 asyncio.run。
3. **重试政策**：只重试明确瞬态失败；读超时可能已有服务端工作。查清 HTTP 层、SDK 层、任务层是否各自重试，防止相乘。
4. **用量语义**：估算、实际统计和预算扣减是三种数；未知用 null，保守保留预留。失败也花费次数和资源，重试不重置总账。
5. **版本一致性**：模型标签可能漂移。维度、模型 digest、前缀、切分和索引版本要一起追踪；维度相同也不代表向量空间相同。
6. **安全错误**：不直接输出 exception、response.text、Pydantic 的原始输入或完整 Prompt；为未知异常设置固定兜底，但不能把错误转换成成功。
7. **测试证据**：mock 证明分支规则，真实小实验确认接口兼容，RAG 固定题集才用于检索/回答质量。不要调验收集后称盲测，不要把 skipped 写成 passed。
8. **可复现交付**：检查 diff、锁版本、输入哈希、命令退出码和实际报告。只提交需要的文件，推送后核对远端提交，不把本地通过写成远程 CI 通过。

AI 可以帮助起草接口、实现重复通信代码、补用例与整理报告；你必须独立审核契约、失败政策、测试预期和证据，能现场解释或改动一个失败分支。今日训练对应 AI Coding 的需求分析、任务分解与协作、审查、调试、测试设计和可复现交付；对应实习能力是 Python 后端、LLM 结构化调用、RAG 输入规格和资源控制，属于应用工程准备，不是模型训练或算法研究，也不保证某家公司会考这些具体题。

1. 为什么 HTTP 200、Schema 合法和证据支持必须分开判断？
2. 超时且 Token 未知时，为什么重试仍要扣次数并保留预算？
3. 哪些结果来自 mock、真实模型和未执行检查，各自能证明什么？
